# ファイル参照の記述規約

ハーネス配布対象（`opencode/` 配下）の Markdown・テンプレートに
ファイル参照を書く際の記述規約を記録する。

## 規約

- **散文（コードフェンス外）**: ファイル参照は「バッククォート ＋ 展開後フルパス」で書く
  - 例: `.opencode/standards/principles/network-resilience.md`
  - 例: `design/token-ssot.json`
  - ルート配置ファイル（`AGENTS.md` / `ARCHITECTURE.md` / `DESIGN.md` / `opencode.json`）は展開後フルパスがルートそのものなので、バッククォートのみ付与
- **コードフェンス内**: フェンス種別で書式を使い分ける
  - **ツリー図（ディレクトリ構成・分岐選択）**: バッククォートを**付けない**・**ベース名で統一**
    - フェンス全体がリテラル・コード文脈であるため、バッククォートは冗長かつ見た目のノイズになる
    - 隣接行（`→ mobile.md` / `package.json` 等）と同一のベース名裸表記に揃える
  - **プロンプト例・判断ブロック・チェックリスト**: ファイル参照は「フルパス ＋ バッククォート」で統一する
    - 検索・実行の対象を一意に特定するため、フルパスが有益
    - 散文と同一の表記（バッククォート＋フルパス）に揃えることで、フェンス内外で参照表現が分岐しない
    - ルート配置ファイル（`ARCHITECTURE.md` 等）はバッククォートのみ

## 根拠（Why）

AI エージェントが「これはファイル参照か、他の何か（概念・コマンド・単語）か」を
余計な判断なしに判別できるようにするため。
- 散文では裸のファイル名がプローズに埋まり、文脈から推測が必要になる → バッククォートでリテラルであることを明示する
- コードフェンスは既に「コード・パス一覧」というコンテキストを確立している → バッククォートの追加判断余地（＝冗長信号）になるため付けない
- ツリー図の目的は「構造の把握」であり、ベース名の索引で十分。一方プロンプト例・判断ブロックは「どのファイルへ実行・検索するか」を一意に特定する必要があるため、フルパス＋バッククォートが有益
- 実コード例（`//` コメント・構文サンプル等）はコード本文として扱うため、バッククォートを付けない（コード内のファイルパスはコードの一部）
- 検索クエリ例（`[File に記載の値]` 等）は置換プレースホルダとして機能するため、内部のパスにバッククォートを付けない

## 対象外（バッククォートの対象にしない）

- JSON 配列・オブジェクトの値（`opencode.json.template` の `instructions` 等）。機械可読で既にパス文字列として決定的
- Design Token 参照値（`"$value": "{primitive.shadow.md}"` 等）。トークン名でありファイル参照ではない
- 検索クエリ例示（例: `[ARCHITECTURE.md の「言語」値] load testing tool ...`）
- TS/コード中の実行用引数（`Bun.file("...")` 等）
- ワイルドカード表記（`web-frontend-*.md` 等）は散文ではフルパス名にプレフィックスを付して表記するが、ツリー図内ではベース名のまま
- ユーザー派生プロジェクト固有のルートファイル（`README.md` / `CHANGELOG.md` / `package.json` 等）はプロジェクトごとに置かれるため、ベース名のままが妥当

## 検証方法

検証は以下の3層で行う。

### 1. 散文（フェンス外）の裸ファイル参照・フェンス内バッククォートの機械走査

コードフェンス除去 + バッククォート区間除去後にファイル参照パターン
`(?<![\w./-])([\w./-]+\.(?:md|json|ts|...))(?![\w.-])` で走査して 0 件であることを確認する。

### 2. 展開後実在パスとの実地照合（推奨・最重要）

`opencode/setup-harness.sh` を一時ディレクトリで実行し、展開後の実在ファイルセットを取得して、全バッククォート付き参照がそのセットに含まれることを確認する。

```
YORI_HAS_UI=y YORI_QUALITY_STRATEGY_CHOICE=1 YORI_USAGE_GIT_CHOICE=1 bash opencode/setup-harness.sh
find . -type f | grep -v node_modules | sort > deployed-files.txt
```

この検証でのみ、参照先が展開時に存在しない問題（例: `design/*.json.template` 残留）を検出できる。
ソース読解だけでは見落とすため、規約変更・setup 変更時は必ず実地照合を実施する。

### 3. 重複ベース名の参照先確認

同名ファイル（principles と instructions の両方に存在するもの等）への参照は、文脈で参照先を判定して確認する：
- 判断基準・詳細・「〜を参照」→ `.opencode/standards/principles/`
- 常時読込・イベント駆動注入・「ベースルール（常時読込）」→ `.opencode/instructions/`
- ルート配置ファイル（`AGENTS.md` 等）はバッククォートのみ
