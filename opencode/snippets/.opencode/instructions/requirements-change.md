# 要件変更の検出と反映ルール

検出は自律的に行うが、変更の適用は必ず人間の承認を得てから実行する。

---

## Full Flow（会話ベースの要件変更）

### 自律トリガー（検出のみ。承認ゲートを通過するまで変更を適用しない）

#### 条件1：人間が目標の変更を明示した

「要件が変わった」「目標が変わった」「方針変更」「XX機能を追加」「XX機能をやめる」など、目標そのものの変更を示す発言。

#### 条件2：指示が Must/Won't と矛盾する

人間の指示が `docs/project-definition.md` の Must または Won't に明らかに反する場合。
Should/Could は対象外。

### 実行手順

1. **確認**：「`docs/project-definition.md` の [該当項目] を [新しい内容] に変更するという認識で正しいですか？」
   と1文で確認する
2. **承認ゲート**：人間が「はい」と回答するまで次の手順に進まない。人間が「いいえ」と回答した場合は
   変更を適用せず、要件変更の検出を終了する
3. **`docs/project-definition.md` 更新**：承認された変更を反映する
4. **波及チェック**（承認が必要）：変更内容が他のファイルと矛盾しないか確認する。
   各ファイルについて、判断に必要な参照ファイルを必ず読んでから確認し、必要な変更を人間に提案する：
   - `ARCHITECTURE.md`：`.opencode/standards/architectures/_how-to-choose.md` を読み、
     フローチャートと「迷いやすいケースの補足」に従って変更後の要件に合うアーキテクチャを判断する。
     現行アーキテクチャのままが妥当 → 現行アーキテクチャファイルを再読して整合を確認する
     変更が必要 → 新しいアーキテクチャファイルを読み、修正を提案する。
     選択肢が複数ある場合は理由とともに提示して人間に選んでもらう
   - `AGENTS.md`：`.opencode/instructions/agents-fill-guide.md` を参照し、
     Project Overview・Commands の修正を提案する
   - `.opencode/project-context.md`：プロジェクト概要の修正を提案する
5. **記録**：変更内容と理由を `decisions/[連番]-[内容を表すslug].md` に記録する（`decisions/000-template.md` をコピーして使用する。技術選定の場合は選定技術の詳細・非機能要件のセクションも記入する）
6. **報告**：すべての更新内容を報告する

### 自律更新が許可されている項目（承認不要）

以下の項目はプロジェクトの成長に伴う技術的・構造的な変化であり、確認なしで更新してよい：

- `ARCHITECTURE.md` の「## ディレクトリ構成」セクション（新しいディレクトリ作成時の追記）
- `.opencode/project-context.md` の「現在のタスク」

### 適用範囲外（要件変更として扱わないもの）

- バグ修正（既存要件の実現）
- コードのリファクタリング（機能追加を伴わない）
- パフォーマンス改善（機能追加を伴わない）
- UXの改善（機能追加を伴わない）

---

## Light Flow（編集時の整合性チェック）

`docs/project-definition.md` / `ARCHITECTURE.md` / `AGENTS.md` のいずれかを編集したとき、
編集内容が他の2ファイルと矛盾しないか確認する。

1. 残りの2ファイルを読み、内容に矛盾がないか総合的に確認する
2. 矛盾あり → 人間に報告し、修正案を提示して承認を得る
3. 矛盾なし → そのまま完了する
