# 認知負荷設計（Cognitive Load Design）

## 核心

「エージェントの視点では、コンテキストウィンドウに届いていないものは存在しない」
（`.opencode/standards/principles/harness-engineering.md`）。
この認識モデルはAI自身の動作管理だけでなく、AIが生成するコードの設計にも適用される。

すべての設計判断は、次の単一の問いに収束する：

> **このコードを将来読むエージェントは、何をどこまで同時に頭へ載せる必要があるか。**

良い設計とは、この「同時に載せる必要があるもの」を最小化し、境界によって
「今は考えなくてよいもの」を明確に分離することである。

## 各原則が答えている認知の問い

| 原則ファイル | 認知の問い |
|-------------|-----------|
| `.opencode/standards/principles/naming-conventions.md` | 値の意味をその場で頭へ戻せる名前か。名前が弱いと、読むたびに意味を再ロードするコストが発生する |
| `.opencode/standards/principles/file-size-and-cohesion.md` | 一つの処理として追える大きさか。一緒に判断する条件が一か所に集まっているか |
| `.opencode/standards/principles/directory-structure.md` | 構成を見ただけで依存と責務を推測できるか。関心の分離が物理的に表現されているか |
| `.opencode/standards/principles/code-quality.md`（可読性） | 関数名・変数名だけで意図が伝わるか。コメントなしで読めるか |
| `.opencode/standards/principles/code-quality.md`（複雑性） | コードの認知的負荷は測定可能な範囲内か。分岐が脳内で追い切れるか |
| `.opencode/standards/principles/ssot-and-constants.md` | 同じ事実を複数の場所で判断していないか。一貫性を頭で覚える必要がないか |
| `.opencode/standards/principles/design-contract.md` | デザインの意味をコンポーネント間で再発見しなくて済むか |
| `.opencode/standards/principles/subagents.md` | サブエージェントの文脈分離はAI版のBounded Context。独立コンテキストで自己評価バイアスを排除する |

## 設計の順序

実装に入る前に以下の順序で判断を進める：

1. **意味**（`docs/project-definition.md`）: この機能の業務上の目的は何か
2. **判断**（`docs/spec.md` / `docs/working/`）: この機能を実現するために何を同時に正しく保つ必要があるか
3. **認知境界**: その判断単位はどのエージェント・どのファイルが一貫して扱うべきか
4. **実装**: 境界をファイル・関数・型定義・APIに落とす

この順序を飛ばして実装から入ると、認知境界が実装の都合で決まり、後で修正が難しくなる。

## 設計判断時の思考フロー

設計判断に迷ったときの内省の問い：

1. **このコードを読むエージェントは、何を同時にコンテキストに載せる必要があるか**
   - その情報は一か所に集まっているか、複数ファイルをまたぐか

2. **名前だけで意味が伝わるか、それとも値を追う必要があるか**
   - 変数名・関数名を見て、中身を読まずに意図を理解できるか

3. **この境界の外の事情を、読む側はどれだけ覚えておく必要があるか**
   - APIの内部実装・呼び出し順・副作用・エラーの種類を、呼び出し側が知る必要があるか

4. **この変更に必要な条件は一か所で確認できるか**
   - 前提条件・不変条件・失敗条件が同じ場所に書いてあるか、それとも分散しているか

## 設計時の認知境界セルフチェック

新しいモジュール・関数・API境界を作成する前に、設計の内省として以下を確認する。
レビュー手順ではなく、設計判断を支える思考の枠組みとして使う。

1. **このコードを読む相手は実装意図を知っているか**
   サブエージェント（code-reviewer / security-auditor）は実装意図を知らない。
   引き継ぎ後の別セッションも同様。コードと名前だけで意図を伝えられるか。

2. **この境界で何を判断するのか**
   「データを保存する」ではなく「この注文を確定可能か判断する」の形で書けるか。

3. **一緒に頭へ載せる必要があるものは何か**
   状態・前提条件・不変条件・失敗条件。それらは今一か所に集まっているか。

4. **何を頭へ載せなくてよい状態にするか**
   外部APIの内部実装・保存形式・通知文面など、この境界の外に置けるものは何か。

5. **境界を越えるとき何を翻訳するか**
   API・イベント・型・エラー形式。呼び出し側は何を約束され、何を自分で処理するか。

6. **非認知の制約は何か**
   性能・トランザクション・セキュリティ・既存コード。認知的理想との折り合いをどうつけるか。

---

## 非認知制約の考慮

認知的に理想的な境界が、以下の制約によって変更できるとは限らない：
- 性能要件（レイテンシ・スループット）
- トランザクション境界（ACID）
- 外部API・既存システムとの整合性
- セキュリティ・コンプライアンス
- リリース期限・運用コスト

認知負荷設計は「絶対的な正解」ではなく「まず考えるべき問い」を提供する。
最終判断はこれらの制約とのトレードオフで決まる。
